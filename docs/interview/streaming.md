# 流式输出（SSE 与 WebSocket）

共 **18 题**，题号 **580–597**。 [返回分类总览](./)

> 答案用于面试复习与工程讨论；【推导】保留原文标记，表示题意依据不完整截图补全。实现细节请结合项目锁定的版本验证。

## 580. 【推导】Agent 场景下 SSE 与 WebSocket 怎么选？ {#q-580}

**参考答案：**

服务端生成输出、通知加 REST 控制通常用 SSE 简单；双向低延迟控制、音频/协作可用 WebSocket。比较网络环境、鉴权、恢复和代理支持，协议选择不会自动解决 run 状态一致性。

## 581. 【推导】Server-Sent Events（SSE）是什么？适用于哪些场景？ {#q-581}

**参考答案：**

SSE 是 HTTP 上的 UTF-8 事件流，适合模型文本、任务进度、通知等服务器单向推送。原生 EventSource 有自动重连，但服务器仍需实现历史事件保存和基于 ID 的续传，不能假设自动重连等于零丢失。

## 582. 【推导】Server-Sent Events（SSE）如何实现服务端事件推送与客户端接收？ {#q-582}

**参考答案：**

服务端以 text/event-stream 输出 event/id/data 行并空行结束，客户端 EventSource 或 fetch 流解析。处理 UTF-8 跨块、CRLF 和多行 data，断连清理订阅；鉴权、心跳和历史恢复独立设计。

## 583. SSE 与 WebSocket 的区别？ {#q-583}

**参考答案：**

SSE 单向、HTTP 友好、文本事件，WebSocket 双向且支持二进制。SSE 常配 REST 上行，WebSocket 需自建重连与业务恢复；二者都要流控和权限，不能把长连接等同可靠消息队列。

## 584. 【推导】流式事件 Envelope 协议层应包含哪些字段？如何支持标识、排序和版本演进？ {#q-584}

**参考答案：**

Envelope 含 eventId、runId、seq、type、schemaVersion、timestamp、step/callId 和 payload。seq 通常在单 run 内递增，eventId 用于去重，schemaVersion 支持演进；不要依赖客户端到达顺序作为唯一顺序。

## 585. 【推导】断线重连与事件续传怎么做，才能避免事件丢失或重复处理？ {#q-585}

**参考答案：**

服务端保存有序事件，客户端提交最后确认游标/Last-Event-ID 并按 eventId 去重。快照附对应水位，再重放其后事件；游标过期时明确要求全量同步，做到至少一次传输加幂等应用而非假设绝不重复。

## 586. 【推导】服务端与客户端的 buffer 策略分别怎么设计？ {#q-586}

**参考答案：**

服务端限制单连接/单 run 缓冲，关键事件持久化，文本增量可合并，慢消费者断开后续传。客户端批量应用、限制未渲染队列与历史占用；不可丢终态、审批和计费等关键事件。

## 587. 【推导】Nginx 与反向代理对 SSE/WebSocket 有什么影响？如何配置缓冲和超时？ {#q-587}

**参考答案：**

代理可能缓冲响应、压缩积攒分块或在空闲时断开；SSE 路由按需关闭 proxy_buffering、配置合适读超时并及时 flush。WebSocket 配置升级头与长连接超时，具体语法按 Nginx/网关版本测试。

## 588. 【推导】tool 调用过程如何流式透出，而不暴露敏感参数或无关细节？ {#q-588}

**参考答案：**

使用 tool.started/progress/completed/failed 等事件，只公开名称、目的、阶段、脱敏参数和结果摘要。敏感原始返回存受控日志/对象引用，UI 依据 callId 关联；避免把内部 schema 或机密直接广播给所有订阅者。

## 589. 心跳与空闲连接保活应该怎么做？ {#q-589}

**参考答案：**

SSE 可发送注释心跳如 : ping 后空行；WebSocket 可用协议 ping/pong 或应用心跳。间隔小于最短代理空闲超时，带抖动并检测超时失联；心跳表示连接存活，不代表任务取得进展。

## 590. 【推导】背压（backpressure）在 Agent 流式输出中如何处理？ {#q-590}

**参考答案：**

写入端观察缓冲阈值/可写信号，按消费速度暂停或合并非关键增量，队列设置硬上限。关键事件先持久化，极慢消费者断开后恢复；不能仅在前端少渲染，却让服务端无限积压。

## 591. 【推导】移动端弱网与前后台切换下，流式连接如何恢复和保持状态一致？ {#q-591}

**参考答案：**

页面恢复前台后重新鉴权，拉取 run 快照与缺失事件，再接续实时流；退避重连并保存游标。后台连接断开不取消任务，网络状态不等于服务端状态，重复事件去重并保持消息归属。

## 592. 【推导】流式协议层与 UI 渲染层的边界怎么划分？ {#q-592}

**参考答案：**

协议层负责字节解码、事件解析、顺序、重连与错误，UI 层负责展示、交互、节流和滚动。通过稳定领域事件/状态仓库连接，避免组件直接解析原始网络 chunk 或依赖供应商事件格式。

## 593. 【推导】同一用户多 Tab 或多设备订阅同一个 run 时，如何管理连接和事件分发？ {#q-593}

**参考答案：**

每个连接独立鉴权和游标，后端广播同一持久 run 事件，设用户/租户连接额度。可用浏览器共享连接降低成本，但权限/断开独立处理；多个订阅者不应导致同一个 run 执行多次。

## 594. 【推导】流式不可用时，REST 轮询降级怎么设计？ {#q-594}

**参考答案：**

提供 GET run 和 events?after=cursor，轮询间隔按状态退避并加抖动，终态停止。快照版本/ETag 降低流量，恢复实时流时按水位去重，轮询不能靠文本长度推测进度。

## 595. 【推导】流式端点的鉴权与连接期间权限变化如何处理？ {#q-595}

**参考答案：**

建立连接时验证身份与 run 权限，长连接按有效期和撤权事件重新验证或关闭。原生 EventSource 不便自定义任意头，可用受控 Cookie 或 fetch 流，避免把长期 token 放 URL；恢复时仍需鉴权。

## 596. 【推导】压缩与分块传输对流式体验有什么影响？ {#q-596}

**参考答案：**

压缩可降低带宽但可能因缓冲延迟首字/增量，需测试 flush 与代理行为；HTTP/1.1 chunk 或 HTTP/2 DATA 帧边界都不等于事件边界。客户端使用流式解码并自行解析完整事件，不能一块当一条消息。

## 597. 【推导】如何把流式协议与 Harness、API 层衔接，形成一致的事件与状态模型？ {#q-597}

**参考答案：**

Harness 写权威状态与事件，API 验证访问并提供 run 快照，流网关按游标推送同一事件日志。统一版本、ID、终态与错误语义，通过 outbox/日志水位避免状态已变但事件丢失，前端支持对账恢复。
