# Tool-Calling

共 **18 题**，题号 **256–273**。 [返回分类总览](./)

> 答案用于面试复习与工程讨论；【推导】保留原文标记，表示题意依据不完整截图补全。实现细节请结合项目锁定的版本验证。

## 256. 【推导】Function Calling 和 Tool Calling 是什么？它们有什么区别与联系？ {#q-256}

**参考答案：**

Function Calling 是让模型输出结构化函数名与参数，Tool Calling 是涵盖函数及其他工具的更广接口表达。模型提出调用请求，实际执行由应用负责；是否自动执行取决于运行时，不是模型直接访问业务系统。

## 257. 【推导】一个好的工具 schema 应该怎么设计？名称、描述、参数和返回值应满足什么要求？ {#q-257}

**参考答案：**

工具应语义单一、名称清晰、说明何时使用，参数有类型、必填、枚举、长度/范围，返回有稳定业务字段与错误码。避免任意 SQL/shell 这类过宽接口，并显式声明副作用、幂等性和权限。

## 258. 【推导】模型什么时候应该调用工具，什么时候应该直接回答或向用户澄清？ {#q-258}

**参考答案：**

需要最新/私有事实或执行动作时调用工具，信息充分的解释题直接回答；缺少无法安全推断的标识或选择时澄清。调用前验证权限与预算，调用后检查结果，不能把模型意图视作动作成功。

## 259. 【推导】读工具、写工具和高风险工具应该如何分类，并设置不同的权限与确认机制？ {#q-259}

**参考答案：**

读工具通常允许自动执行但仍需 ACL；写工具要求明确作用域、幂等与审计；支付、外发或删除等按风险要求确认。确认应绑定具体参数与资源版本，低风险且已有授权的写入不必机械地重复审批。

## 260. 【推导】工具返回结果应该怎么组织，才能让模型准确理解并继续执行任务？ {#q-260}

**参考答案：**

返回结构化数据、成功标志、稳定错误码、来源/时间、分页游标和必要提示。限制大小，过大结果返回可检索引用；错误区分可重试与需修参，文本内容作为不可信数据，不夹带高优先级指令。

## 261. 【推导】工具调用失败后，应该重试、换工具还是停止？如何设计失败处理策略？ {#q-261}

**参考答案：**

瞬时网络/限流可在预算内指数退避加抖动，参数错误应修参，权限错误需停止或申请合法授权。换工具也要保持同一意图与安全边界；状态不明的写操作先查询结果，避免盲重试。

## 262. 【推导】为什么幂等性是写操作工具的底层要求？如何避免重试造成重复副作用？ {#q-262}

**参考答案：**

网络超时不代表服务端未执行，重试可能重复扣费或创建记录。用租户+操作+幂等键建立唯一约束、保存请求摘要与结果，事务内落库；同键不同参数拒绝，重放返回原结果。

## 263. 【推导】多个工具能不能并行调用？如何处理依赖关系、执行顺序和结果合并？ {#q-263}

**参考答案：**

没有数据依赖且不冲突的读任务可并行，依赖步骤按 DAG 顺序执行，对同一资源写入用锁/版本条件等控制。限制并发并定义部分失败策略，结果按调用 ID 合并而非完成顺序。

## 264. 【推导】长耗时工具和异步任务怎么接入 Agent？如何处理任务状态、超时和结果回传？ {#q-264}

**参考答案：**

工具先返回 jobId 和可查询状态，执行异步入队，完成后通过事件/Webhook 或轮询回传。持久化关联 runId，设置超时、取消、幂等与 TTL；暂停等待时不应占住线程持续忙轮询。

## 265. 【推导】Tool Calling 的流式输出怎么设置和处理？如何拼接、校验并执行工具调用参数？ {#q-265}

**参考答案：**

按 callId 和索引累积名称/参数片段，等待完整结束后 JSON 解析、schema 和业务权限校验，再执行。不能把不完整 JSON 边到边执行，须处理多个交错调用、截断与重复终止事件。

## 266. 【推导】工具参数校验应该放在哪里？模型侧约束和服务端校验分别承担什么职责？ {#q-266}

**参考答案：**

模型侧 schema 降低生成错误，服务端是最终可信边界，必须验证类型、长度、枚举、业务约束、身份与资源权限。数据库约束保护最终一致性；即使开启严格输出，也不能跳过服务端授权。

## 267. 【推导】为什么不应该把原始业务 API 直接暴露给模型？如何封装适合 Agent 使用的工具？ {#q-267}

**参考答案：**

原始 API 往往字段冗余、内部语义复杂或权限过宽，应封装成面向意图的窄工具，如 create_draft 而非任意 HTTP。显式设置默认值、分页、幂等、错误和结果摘要，隐藏内部凭据与实现细节。

## 268. 【推导】工具太多时模型会选错，应该怎么组织、筛选和动态加载工具？ {#q-268}

**参考答案：**

按领域和任务检索工具目录，先加载少量相关 schema，必要时再发现更多能力。避免近义重复命名，版本化描述并测选择准确率；工具发现必须受权限过滤，不能检索到就自动获得执行权。

## 269. 【推导】Tool Calling 的日志和可观测性应该记录哪些信息，如何定位调用问题？ {#q-269}

**参考答案：**

记录 runId/callId、工具版本、脱敏参数摘要、授权结果、起止时间、重试、错误码与结果引用。把模型选择、参数校验、执行和下游请求分成 span，区分选错工具、填错参数和工具本身失败。

## 270. 【推导】工具调用怎么做测试？只测最终答案是否足够，还应该验证哪些过程行为？ {#q-270}

**参考答案：**

除最终答案还测工具选择、参数合法性、调用顺序、权限拒绝、超时、重试、幂等与取消。使用 mock 固定模型不确定性，再做沙箱集成与端到端测试，验证未产生禁止的副作用。

## 271. 【推导】如何处理模型乱填工具参数、漏填必填参数或使用无效参数的情况？ {#q-271}

**参考答案：**

结构化校验后返回可理解的字段级错误，在有限次数内允许模型修正；缺失业务事实需询问用户或查询权威数据。不要静默猜填 ID、权限或金额，非法字段应拒绝而不是直接传给下游。

## 272. 【推导】Function Calling、MCP 和普通 API 调用有什么区别与联系？ {#q-272}

**参考答案：**

普通 API 是应用间业务调用；Function Calling 是模型表达调用意图的机制；MCP 是主机与外部能力服务器的发现/调用协议。可将 MCP 工具转换为模型工具定义，再由运行时经 MCP 调用业务 API。

## 273. 【推导】Tool Calling 中写操作为什么必须设置权限、确认与审计机制？ {#q-273}

**参考答案：**

写工具能改变真实系统，模型误判、注入和重试会扩大副作用。执行端应检查主体权限与参数，按风险绑定有效授权/确认，记录审计并支持幂等和补偿；是否逐次确认取决于风险和既有授权。
