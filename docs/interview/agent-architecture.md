# Agent 架构

共 **15 题**，原始题号 **557–571**。 [返回分类总览](./)

> 答案用于面试复习与工程讨论；【推导】保留原文标记，表示题意依据不完整截图补全。实现细节请结合项目锁定的版本验证。

## 557. 常见的 Agent 架构模式有哪些？ {#q-557}

**参考答案：**

常见有 ReAct 循环、计划—执行、固定 Workflow、Router、Orchestrator–Worker、Supervisor 和事件驱动模式。根据任务不确定性、依赖、风险与并行收益选择，通常是确定性骨架加局部自主节点。

## 558. 【推导】Agent 的核心循环 Observe–Think–Act 如何工作？如何判断继续执行或结束？ {#q-558}

**参考答案：**

Observe 收集环境和工具结果，Think 选择下一步，Act 经验证后执行，再把反馈写回状态。每轮检查验收、阻塞、取消和预算，完成依赖结果验证而非仅凭模型说“完成”。

## 559. 【推导】单 Agent 和多 Agent 架构怎么选？各有什么收益、成本和适用场景？ {#q-559}

**参考答案：**

单 Agent 简单、共享上下文容易且成本低；多 Agent 可并行独立任务或隔离专业能力，但增加消息、整合和失败成本。先测单 Agent 基线，只有可分解收益明显时才引入多个执行单元。

## 560. 【推导】Orchestrator–Worker 和 Supervisor 架构有什么区别？如何分工与协调？ {#q-560}

**参考答案：**

Orchestrator–Worker 通常由协调者分解相对独立任务并汇总；Supervisor 更强调持续观察、选择下一代理和干预。两者可以重叠，名称非统一标准，应说明真实控制权、状态所有者和终止机制。

## 561. 【推导】Router / Dispatcher 架构什么时候适用？如何实现任务路由和分发？ {#q-561}

**参考答案：**

Router 适用于任务可按领域、语言、模态或复杂度分派至不同模型/流程。可用规则、分类器或模型路由，带置信阈值、默认路径和升级策略；记录误路由成本并避免跨权限域传递数据。

## 562. 【推导】Agent 分层架构怎么拆分？模型层、编排层、工具层等分别承担什么职责？ {#q-562}

**参考答案：**

入口层负责认证/会话，编排层负责状态机与预算，模型层做推理适配，工具层执行受控动作，数据层保存状态/知识，观测层贯穿链路。层间使用清晰契约，权限检查不能只放在入口。

## 563. 【推导】确定性 Workflow 和自主 Agent 怎么选择，如何组合？ {#q-563}

**参考答案：**

确定性 Workflow 适合稳定、可审计流程，Agent 适合开放步骤和语义决策。常用 Workflow 固定审批、事务和异常恢复，在检索/分析等局部放自主节点，输出必须通过契约校验才能推进。

## 564. 【推导】Human-in-the-loop 应该插在架构的哪些位置？如何设计人工确认与恢复执行？ {#q-564}

**参考答案：**

在缺关键输入、风险动作前、计划越界或恢复失败时设置人工节点。先持久化待决策状态和具体参数，审批绑定版本与有效期；恢复需重新鉴权并防止重复执行，不能只阻塞内存里的函数。

## 565. 【推导】有状态和无状态 Agent 服务怎么选择？如何管理会话状态与扩缩容？ {#q-565}

**参考答案：**

有状态逻辑有利于连续任务，但进程内保存会限制扩缩和恢复。常见方案是无状态 API/worker 加外部数据库、检查点和租约；同一 run 通过版本锁/队列串行推进，缓存不是唯一事实源。

## 566. 【推导】Copilot 架构和 Autonomous Agent 架构有什么区别？如何确定自主执行边界？ {#q-566}

**参考答案：**

Copilot 以用户持续选择和触发为主，Autonomous 在授权范围内自行推进更长任务。自主边界应按工具、资源、风险和时间定义，提供可见进度、暂停、取消与审查，而不是只有一个“全自动”开关。

## 567. 【推导】上下文架构怎么设计？系统态、任务态和会话信息如何组织与隔离？ {#q-567}

**参考答案：**

系统态保存规则和可用能力，任务态保存目标/计划/工具结果，会话态保存对话和用户交互。分层存储并按需组装，跨租户、跨 run 隔离；当前有效状态优先于被裁剪的聊天文本。

## 568. 【推导】长任务 Agent 怎么架构？子任务、状态持久化和中断恢复怎么设计？ {#q-568}

**参考答案：**

长任务拆成可验证子步骤，持久化状态、结果引用、事件与外部操作 ID，使用队列驱动 worker。检查点与幂等恢复结合，支持暂停/取消和进度订阅，避免用一条超长 HTTP 请求承载全部执行。

## 569. 【推导】Event-driven Agent 架构适合什么场景？如何处理事件触发、去重和异步执行？ {#q-569}

**参考答案：**

事件驱动适合告警、Webhook、文档更新等触发任务；事件带 ID、来源和实体版本，先鉴权去重再入队。乱序用序号/版本处理，失败进入重试/死信，业务写入与事件发布用 outbox 等保障。

## 570. 【推导】失败恢复和 Checkpoint 在架构中怎么设计？如何恢复任务并避免重复副作用？ {#q-570}

**参考答案：**

在可恢复边界保存输入、状态、步骤版本、工具调用及结果引用，恢复时确认外部动作最终状态。持久化和外部副作用通常不能原子完成，所以需要幂等键、事务 outbox 或补偿，而不只存 messages。

## 571. 【推导】从 Demo 架构迁到生产架构，最需要优先补齐哪些能力？ {#q-571}

**参考答案：**

优先让状态和副作用可控：鉴权、数据隔离、持久化、幂等、超时取消、观测与回归评测。之后再拆微服务或多 Agent；架构演进应由故障、负载和团队边界驱动。
