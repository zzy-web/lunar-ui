# 向量数据库与存储

共 **15 题**，题号 **419–433**。 [返回分类总览](./)

> 答案用于面试复习与工程讨论；【推导】保留原文标记，表示题意依据不完整截图补全。实现细节请结合项目锁定的版本验证。

## 419. 【推导】Agent 会话存储如何选型？OLTP、Redis 等方案分别适合哪些需求？ {#q-419}

**参考答案：**

OLTP 如 PostgreSQL 适合会话、run、审批等一致性记录；Redis 适合缓存、限流、短期锁或临时状态。选择按事务、查询、保留周期与吞吐，不能让易失缓存成为必须恢复状态的唯一来源。

## 420. 【推导】run state 在存储层应该持久化什么？如何确定保存粒度和恢复边界？ {#q-420}

**参考答案：**

保存目标、输入引用、状态版本、步骤、工具请求/结果、审批、预算用量、配置版本和产物位置。按可恢复边界落盘，token 增量可批量记录，关键副作用前后需单独确认；过细增加写放大，过粗难恢复。

## 421. 【推导】向量数据库选型应该看哪些工程维度？如何评估性能、过滤能力、成本和运维复杂度？ {#q-421}

**参考答案：**

评估召回率—延迟曲线、过滤与 ACL 能力、更新/删除、维度、规模、备份、高可用、成本和团队运维。用真实向量及过滤分布压测，不能只用无过滤的厂商峰值 QPS 选型。

## 422. 【推导】OLTP 与向量库之间的混合存储怎么设计？如何保持数据关联与一致性？ {#q-422}

**参考答案：**

OLTP 保存权威原文/元数据与 ACL，向量库存可重建检索索引，通过 docId/chunkId/version 关联。用 outbox/CDC 异步同步并记录索引版本，生成前重验权限和删除状态，处理最终一致性的短暂窗口。

## 423. 【推导】向量 metadata schema 怎么设计？如何支持过滤、权限控制和数据管理？ {#q-423}

**参考答案：**

至少包含 tenantId、docId、chunkId、source、contentVersion、embeddingVersion、更新时间及 ACL/标签字段。过滤字段要可索引且类型稳定，权限以权威服务为准；不能只在生成后通过 Prompt 过滤越权内容。

## 424. 【推导】向量索引策略 HNSW、IVF、PQ 有什么区别？如何按需求选择？ {#q-424}

**参考答案：**

HNSW 用邻近图获得高召回，内存与更新成本较高；IVF 先聚类再搜索部分桶，需训练和调参；PQ 压缩向量节省内存但损失精度。可组合使用，按规模、过滤、更新和召回要求实测。

## 425. 【推导】向量库与 OLTP 的备份恢复策略如何设计，如何保证恢复后的数据一致性？ {#q-425}

**参考答案：**

OLTP 做全量/增量与时间点恢复，向量索引保存快照或从带版本原文重建。使用一致的恢复水位、变更日志和删除 tombstone，对账文档/索引版本；只分别备份而无关联点会恢复出错配数据。

## 426. 【推导】多租户向量隔离有哪些方案？各自有什么优缺点和适用场景？ {#q-426}

**参考答案：**

可按租户独立实例、独立 collection/namespace 或共享索引加 tenant 过滤。前者隔离强但成本高，后者资源利用好但易配置失误；根据监管/规模分级部署，服务端强制过滤并做越权测试。

## 427. 【推导】embedding 版本升级时如何不停服迁移向量数据和索引？ {#q-427}

**参考答案：**

新旧 embedding 分别使用独立版本/索引，后台回填并对新增内容双写，影子查询比较召回。达到质量/完整性后切流，保留回滚窗口；不同维度/模型的向量不能直接混入同一相似度空间。

## 428. 【推导】checkpoint 存储在工作流与长任务场景中应该如何设计？ {#q-428}

**参考答案：**

检查点包含可序列化状态、schema/流程版本、步骤游标和外部结果引用，支持原子写与并发版本控制。大对象存对象存储、数据库存引用与校验；加密、保留和恢复演练同样重要。

## 429. Agent 存储成本怎么拆账与优化？ {#q-429}

**参考答案：**

拆分会话/事件 OLTP、原文/附件对象存储、向量索引、缓存和备份费用，按租户/项目归因。优化重复内容、切块数、冷热层级、保留期与向量精度，不因节省索引成本牺牲必要 ACL 与恢复数据。

## 430. 【推导】从 PoC 到生产的存储迁移路径怎么规划？如何控制迁移风险？ {#q-430}

**参考答案：**

先设计稳定 ID、schema 和导出能力，POC 单库存储也保持清晰边界。迁移使用双写/回填/校验/影子读与分批切流，保留回滚和增量追平机制；避免一次性停机搬运无验证数据。

## 431. 【推导】session store 与记忆系统模块的职责边界是什么？如何关联和协作？ {#q-431}

**参考答案：**

session store 管对话、run 关联和执行历史，Memory 管经筛选的长期事实/偏好与检索。通过用户/租户 ID 与来源事件关联，删除和纠错传播到记忆，不能把每条聊天自动当成永久事实。

## 432. 【推导】run 历史与 audit 日志应该如何落库？如何支持查询、追踪和审计？ {#q-432}

**参考答案：**

run 历史按任务和步骤可查询，事件可追加存储，审计单独保存主体、授权和副作用证据。以 runId/callId 关联，关键记录防篡改并限制访问；调试日志采样不能导致关键审计缺失。

## 433. 【推导】冷热分层与 TTL 策略如何设计，如何平衡存储成本、查询性能和保留需求？ {#q-433}

**参考答案：**

近期 run/事件放热库，旧正文和附件转对象存储，索引按访问需求重建。TTL 按数据类型、用户删除和业务保留要求设定，引用与派生数据同步清理，恢复中的 run 和审计保留不得被盲目过期。
